Errors & Debugging

Getting errors and spending time debugging is a major part of programming.

Client-side errors

Client-side errors are shown in the browser console.

To see the client-side errors you need to use DevTools. You can also write directly in the browser console. 

let flag;
flag.color;

Writing the above code in the browser console, will give an error, since flag is undefined. 

Uncaught TypeError: can't access property "color", flag is undefined
    <anonymous> debugger eval code:1

The error description depends on which browser is being used. In this example, I am using Firefox, and here the error description is pretty clear: color can't be accessed since flag is undefined.

The debugger-keyword can be a helpful tool for client-side errors.

When using Firefox, open the Debugger window in DevTools. You will be able to see, that the code pauses where the debugger keyword is. 

let flag; // flag: undefined
debugger; // the code stops here
flag.color;

You can see that flag is undefined. At the top of the viewport, there is a pop-up that says "Debugger paused" and shows the option to either run the code or step-over. Step-over will run one line of code, and pause at the next one. This can be helpful if the error message isn't clear to you. It lets you see the values of the variable step-by-step before the error occurs. It gives a clear look into how the code is working and what is happening.

Server-side errors

Server-side errors are shown in the terminal.

If you wrote code like this:

let flag;
flag.color;

You would get a server-side error, since the flag is undefined and it isn't possible to find the color on an undefined flag. 

<ABSOLUTE_PATH>/app.js:2 # name of the file is app.js, and the error happened on line 2
flag.color; # the error occurred at this specific char
     ^

TypeError: Cannot read properties of undefined (reading 'color') # error description
    at Object.<anonymous> (<ABSOLUTE_PATH>/app.js:2:6) 
    # name of file and line number again. The 6 is the chars from the left margin.
    at Module._compile (node:internal/modules/cjs/loader:1761:14)
    at Object..js (node:internal/modules/cjs/loader:1893:10)
    at Module.load (node:internal/modules/cjs/loader:1481:32)
    at Module._load (node:internal/modules/cjs/loader:1300:12)
    at TracingChannel.traceSync (node:diagnostics_channel:328:14)
    at wrapModuleLoad (node:internal/modules/cjs/loader:245:24)
    at Module.executeUserEntryPoint [as runMain] (node:internal/modules/run_main:154:5)
    at node:internal/main/run_main_module:33:47

The stack trace is the first place to look, when trying to figure out why an error happened. Here, you can find the name of the file, the line number, the chars from the left margin, and the error description. It will also give you a small arrow ^ pointing at the exact char where the error happened. All of this makes it easy to find the exact error, and determine the reason behind it.

If the error is not clear, or it's a hidden bug, then you can isolate the code by commenting out a code-section and uncomment it line by line until the problematic part is revealed.

If you get an error such as:

Error: ENOENT: no such file or directory, stat '<ABSOLUTE_PATH>index.html'

The error is quite clear: no such file or directory, at that specific path. ENOENT stands for Error No Entry

You can write the following in the terminal:

<ABSOLUTE_PATH>index.html

And see if you get an error. If you do, then the file doesn't exist on that path. Maybe it's the wrong filename or path. In this example, the path won't work because of a missing "\". The correct path would be: 

<ABSOLUTE_PATH>\index.html

Error-handling

Using console.log() can be a good way to check if you're getting the expected results, or to see if there is a connection. 

console.log()
// logs to the terminal on server-side and in the browser console on client-side

In the same way, it's a good idea to make a visible change when adding a CSS file, such as a red background. Just to make sure, that the connection is correct.

Error is undefined, if it isn't set. Meaning, it is a false-value as standard. A statement can not run if it is falsy, it can only run if the statement is true. That is how a case like this works: 

if (error) {
  console.log("There was an error", error);
  return;
}

console.log("Everything worked out as hoped.");

Rubber duck debugging

Rubber duck debugging, also known as rubberducking, is a simple idea: talk to someone.

In rubberducking there isn't a need for feedback or help from the other person. The important part is explaining the code out loud, step by step. Since the other person doesn't need to participate an inanimate object such as a rubber duck or a teddy bear can be put in place of a person.

It can be helpful to step away from finding a solution, and instead focusing on the purpose of the code. Some helpful questions to answer are:

  • What is your expected outcome from the code?
  • How does the actual outcome differ from your expectations?
  • Step through the code and identify discrepancies
  • Analyze the observed behavior. Why might the output be as it is?
  • Explore potential adjustments to the code and apply them
